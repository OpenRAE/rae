**Milestone 67: participant-control architecture and adversarial implementation audit**

Review date: 2026-09-21. Audited development revision: `6bfdb7efdabbf5efe22fa023a16316830cf25380`.

**Exploration status, 2026-09-21:** This audit is retained as input to [Runtime Refactor exploration #1348](https://github.com/OpenRAE/rae/issues/1348). Its repair recommendations, sequence, and effort estimates are audit judgments, not agreed requirements or an authorized implementation plan. The [subsequent owner clarifications](../runtime-refactor/README.md) govern the exploration's present framing: current capability parity is the near-term objective; durability does not imply resumption; operational-OT protections are not universal requirements; and concrete backend willingness and contextual refusal are largely backend responsibilities. No refactor architecture or PRD has been defined. Source findings remain scoped to the audited revision; they have not been rerun against the exploration branch's newer base.

**Architecture clarification incorporated 2026-09-21:** The project owner clarified that RAE's runtime is the shared execution engine that drives LilRAE, BigRAE, and other backends. It is a product component alongside SDL and the processor, and may be the only runtime implementation built. The audit's original F01 ownership objection is withdrawn. F01 retains its identifier to make the correction explicit; F02–F16 remain findings. The source evidence and seven counterexamples are unchanged, while the ownership interpretation, ADR dispositions, and repair plan below have been corrected.

**Assessment**

The concern is substantially justified. Several defects originate in the language and architectural model, propagate into contracts, and then become runtime behavior. Repair requires redesigning important parts of the participant-control subsystem and amending architectural decisions. A collection of local bug fixes would leave the main problems intact.

The evidence does **not** support throwing away everything in the milestone. There are sound distinctions in the specifications, useful state-cut and history machinery, and appropriately bounded formal results. The central failure is that these distinctions are repeatedly lost when the system turns declarations into executable controls and evidence. A declared dependency is not necessarily executed; a required profile can disappear; a recorded cancellation is not demonstrated prevention; successful execution becomes purported delivery and observation.

The most consequential problems are:

- The controller model conflates scenario participants with supervisory authority, while its supposedly reusable control policies contain preassigned occurrence revisions and execution order.
- Modular composition admits contradictory or incomplete configurations, does not execute dependencies between providers, and gives unavailable optional advice a veto.
- Several implementation paths cannot establish the effects they record. Inject realization and mixed-backend observation are particularly weak.
- Security depends on deployment boundaries and trusted resolvers that are not adequately represented by the portable guarantees. The HTTP API has no participant-only read role; the strongest decision-surface entry point cannot supply the identity required by governed admission.
- Assurance includes a reference-backend probe that returns a canned transcript while its conformance case calls that a live native observation.

These are reasons to withhold broad claims of effective adversarial participant control. They are not evidence of a demonstrated compromise of LilRAE or BigRAE: neither deployed backend was examined in this review.

**Authority, scope, and method**

[OpenRAE/hub#3](https://github.com/OpenRAE/hub/issues/3) supplies the ecosystem product boundary, including LilRAE's local realization responsibilities and BigRAE's organizational control-plane responsibilities. The project owner's subsequent clarification supplies the runtime interpretation: RAE's shared runtime drives those backends through execution, as part of achieving backend agnosticism. Backend product ownership does not imply a separate scenario runtime in each backend. This audit uses that clarified architecture alongside the milestone's semantic promises.

The execution path is **RAE SDL → processor → shared RAE runtime → backend execution protocols → LilRAE, BigRAE, or another backend**. The agreed role is that the shared runtime drives backend execution. The audit's proposed allocation of coordination, control-state transitions, scheduling, recovery, and outcome verification is an architectural judgment, not a complete agreed responsibility model. Later clarification places concrete ability, willingness, and contextual refusal largely with the backend; RAE cannot assume all of that accountability upstream. The detailed allocation and protocols remain under exploration. References to specific reference backends or finite conformance profiles below describe those artifacts; they do not characterize the product runtime as merely a reference implementation.

All **41 milestone issues** were inventoried, including their discussions and identified delivery changes. At capture, 35 were closed and six open. The review includes the merged implementation of **#1069 in PR #1346**, although the issue remained open. It uses current `origin/dev`, rather than the user's older checkout at `fdc1863d8ca3ddc2ac9f7f679b2a74223016a3c6`, so the conclusions include the latest modular-control runtime work. The audit checkout is separate from that working branch.

Coverage includes authoring and compilation; mixed-control lifecycle; participant views and decision surfaces; crossing policy and final sinks; confidentiality/integrity labels; modular profiles, providers, composition and effects; mixed-backend routing; opacity and bisimulation claims; HTTP authorization; and operation history/recovery. Every milestone workstream was reviewed, with deep inspection of the critical paths. This is not a claim that every line of every touched file was inspected.

The [issue-by-issue scope](scope-2026-09-21.md) accounts for all 41 issues. The [evidence inventory](evidence-2026-09-21.json) records the revisions, delivery commits, affected files, and probe results. References below are pinned to the audited revision.

Findings distinguish direct source behavior, executable contract counterexamples, conditional deployment risks, and architectural judgments. **F01 — Corrected architectural premise: the shared runtime owns execution orchestration. Original ownership finding withdrawn.**

ADR-108 assigns mechanism invocation, exact-cut composition, effect admission, durable commit, histories, and recovery to “RAES runtime,” while assigning concrete mechanisms and installation to backends. That central orchestration role is consistent with the clarified architecture. A `RuntimeControlPlane` owning common execution state and driving backend protocols is appropriate; the amount of orchestration in RAE is not itself a defect. [ADR-108 responsibilities][adr108]

The original finding incorrectly inferred from Hub #3 that each complete backend should be able to supply an independent orchestration architecture, and treated RAE's runtime chiefly as optional reference machinery. The project owner explicitly rejected that premise. This audit withdraws the high-severity ownership objection and the associated recommendation to decide which common execution responsibilities should move out of RAE.

Backend agnosticism should be assessed through the ability of the same runtime to drive different conforming backends. The relevant boundary is between common execution semantics and concrete realization: the runtime coordinates and records an operation, while the backend performs it and supplies the evidence needed to establish its outcome. F04, F12, and F13 identify failures to complete that connection. Their remedy requires a functioning shared execution path, not independent scenario orchestrators in each backend.

Architectural follow-through: clarify the product-runtime role in ADR-104 and related prose while retaining explicit deployment profiles and bounded guarantees. Evaluate established execution, supervision, state-machine, and simulation foundations for use within or beneath RAE's runtime. Preserve the portable backend boundary and one clear authority for execution state; avoid duplicating orchestration and recovery in both a foundation and the existing runtime. This is a direction for the repair work, not a new demonstrated defect or a requirement to build multiple runtimes. [ADR-104][adr104]

**F02 — Scenario participant, controller, and security principal are not properly separated. High language-design defect.**

The mixed-control validator requires a controller to resolve to a declared agent or `self`. The formal participant model explicitly excludes a control-plane identity from being that controller. At runtime, selection of an authorized transition depends on the outgoing state's controller being among the authenticated identity's authorized controller references. [Controller validation][controller-validator] [Normative controller model][participant-model] [Transition selection][transition-selection]

An ordinary out-of-scenario experiment supervisor therefore cannot be represented directly as the controller. The author must introduce an agent into the scenario or arrange credentials to act for the current scenario controller. An emergency intervention by an independent supervisory authority does not naturally fit the model.

Some controllers legitimately are participants. That does not justify requiring all controllers to be participants. A participant is an authored subject of the world; a supervisor exercises scoped authority; an authenticated principal presents credentials. These roles can coincide, but their identity and authority need separate types and explicit relationships.

Repair: redesign controller references and authority grants, including independently authorized intervention and revocation. Migrate authoring, compiled state, API-409 records, and admission checks together. Coordinate this with the already-published [participant-identity audit][identity-audit]; its adjacent remediation work should not be duplicated under new names.

**F03 — Authored policies are finite occurrence scripts, not reusable supervisory transition rules. High language-design defect.**

Each authored `MixedControlTransition` fixes `expected_state_revision`, `resulting_state_revision`, and `effective_order`. Revisions must increment by one; effective orders are globally unique within the declaration; validation establishes reachability through those fixed state/revision pairs. Runtime folding then requires the current revision to match the transition's authored revision. [Transition declaration and validation][transition-model] [Runtime fold][transition-fold]

A reusable “request approval → approve or deny → return to autonomous operation” policy cannot simply repeat. After one cycle, the same transition no longer matches the revision. The author must pre-expand future occurrences, including their order, into the policy. That is a reasonable representation of a bounded schedule or trace, but a poor representation of reactive supervisory behavior whose number and timing of interventions are unknown beforehand.

Authority-window checking has the same problem: it compares the transition's preauthored `effective_order` against preauthored intervals. It does not establish that authority is current at a live execution-time coordinate. This is not a claim of a wall-clock expiry exploit—the declared clock is logical—but a finding that declaration consistency is doing the job of runtime validity. [Authority-window check][authority-window]

Repair: separate policy templates from transition occurrences. The policy declares permitted transitions, guards, authority, and relevant clock; the occurrence binds actual state revision and execution order. Retain a separately named finite-script mode if useful. This changes the language, compiler, contracts, and runtime together.

**F04 — Accepted control records overstate cancellation and intervention effects. High correctness/evidence defect.**

The control-transition path resolves a target, checks the declaration and state, builds an occurrence, appends control history, and commits it. It does not itself invoke backend cancellation or interruption. The cancellation effect is derived solely from the target kind: proposal/decision becomes `PREVENTED`, admitted action becomes `PARTIAL_LIMITATION`, and an attempt becomes `TOO_LATE`. [Transition preparation][control-preparation] [Cancellation classification][cancellation-effect]

That describes a presumed stage-based opportunity to cancel; it does not establish what actually remained cancellable or what was prevented. A concurrently progressing backend may already have crossed the relevant boundary. Inspection of the built-in action path did not establish a corresponding general scheduling/admission interlock that makes the recorded prevention true.

A custom trusted resolver or backend can supply additional enforcement. This review does not conclude that every possible backend ignores cancellation. The problem is that the built-in path records a stronger effect than the evidence it obtains supports, while leaving the consequential enforcement obligation implicit.

Repair: distinguish accepted request, authority/state transition, prevention of new admission, attempted backend interruption, and observed terminal effect. Derive cancellation outcomes from the owning backend's acknowledgments/readback and an explicit race model. Recording a handoff similarly must not stand in for transferring execution control.

**F05 — The v2 decision surface cannot compose with governed action admission. High, localized implementation defect.**

`admit_participant_decision_surface_selection_v2` accepts no identity or crossing-evidence arguments and does not forward them when calling `admit_participant_action`. Governed crossing admission requires a `ControlPlaneIdentity` and the relevant evidence. The older surface path can forward submission options; v2 cannot. [v2 entry point][decision-v2] [Ordinary admission][action-admission] [Identity requirement][crossing-identity]

Consequently, an otherwise valid selection bound to the exact delivered v2 surface cannot use this public entry point with configured governed ingress. Two individually elaborate pieces of the control design do not compose on the normal path.

Repair: carry the authenticated invocation context through binding, revalidation, and admission without allowing selection data to create authority. This is a bounded implementation fix, followed by verification of the actual combined path. ADR-095's decision/delivery distinction should be retained.

**F06 — The HTTP API has no least-privilege participant read role. High conditional security risk.**

Participant retrieval and unrestricted snapshot retrieval share `_ReadIdentity`. Its allowed roles are backend, operator, and auditor. The participant route checks the governed audience binding, but `/snapshot` returns the target's full runtime snapshot under the same read-role gate, including participant control, crossing, and evaluation histories. [Read-role authorization][http-auth] [Participant retrieval][participant-http] [Snapshot endpoint][snapshot-route] [Snapshot model][snapshot-model]

If a client receives credentials to retrieve its own participant view, narrowing its audience binding does not prevent it from using those same credentials to read the wider snapshot. There is no participant-only role in this API to express that restriction.

This is not an unauthenticated disclosure. The API may legitimately be an administrative API used only by trusted backend components. In that deployment, a separate participant-facing adapter must enforce the boundary and must not pass these credentials through. The problem is dangerous ambiguity between participant-scoped endpoints and administrator-scoped API authority.

Repair: explicitly choose and document the trust boundary. Either keep this API strictly administrative and provide a separately scoped participant interface that invokes the shared runtime with authenticated context, or introduce object/participant-scoped capabilities and enforce them across every route, including alternate retrieval paths. The common runtime must preserve the authorization boundary regardless of the selected backend. An audience check on one endpoint is insufficient.

**F07 — Required modular control can disappear without blocking the crossing. High completeness defect; reproduced.**

The modular resolver may return `None`; orchestration passes that through as absence and leaves incumbent gates alone. This path does not establish that the admitted selection's required profiles are optional or inapplicable at this cut. Separately, the selection contract permits a required profile to be represented by a binding with no result slots. [Resolver absence][control-resolver] [Selection validation][control-selection]

Two counterexamples are included in the reproduction artifact: a selection requiring `teaching-influence` with no slots derives `eligible`; an actual runtime binding with that required profile and a resolver returning `None` produces no modular outcome. The latter bypasses composition rather than producing an explicit unsupported or denied result.

The resolver is trusted, so this is not a claim that an untrusted participant can directly return `None`. It is a failure to enforce a core invariant at the boundary: a resolver mistake or unsupported applicability becomes indistinguishable from intentionally absent optional control. MPC-01 says unresolved applicability prevents admission and an absent required selection prevents apparatus admission. This runtime omission establishes neither satisfied obligations nor nonapplicability. [MPC-01][mpc-selection]

Repair: represent absence, proven nonapplicability, unsupported required control, and empty optional selection separately. Validate required-profile coverage through actual obligations, not membership in a list of bindings. This requires a contract change and runtime enforcement.

**F08 — The effect algebra can call a parent crossing eligible while requesting its denial. High semantic contradiction; reproduced.**

The result reducer considers any resolved non-decision payload satisfied. Effect blocking checks predecessor phase, conflicts, and causal bounds; it does not make a `deny` or `withhold` effect on the current crossing prevent that crossing when the effect is marked subsequent. [Result satisfaction][result-satisfaction] [Effect blockers][effect-blockers]

Starting from the published teaching-inject fixture, replacing the effect target with `deny` or `withhold` of the very crossing and subject being composed yields `eligible` with no blockers. The entire evaluation contract validates. A denial of this crossing cannot coherently be deferred until after that crossing is released.

This counterexample establishes a contradiction in the published composition algebra. Trusted-context validation is a further gate; the experiment does not demonstrate a live unauthorized action through it. Nevertheless, a portable contract must not define a self-defeating plan as eligible and rely on each trusted owner to rediscover the contradiction.

There is also a large gap between declared effect kinds and runtime owners. Contracts describe thirteen kinds, but the current dispatch binding supports only `inject` and `handoff`. Unsupported ownership can be discovered while draining effects after the parent evaluation has already committed. Limited backend support is legitimate; the selection/admission boundary must reflect that limit before releasing work that depends on it. [Effect owner bindings][effect-owners]

Repair: distinguish crossing decisions, transformations/prerequisites, and subsequent operations in the type system. Enforce target/phase compatibility and supported realization before eligibility. Replace the generic “resolved effect request is satisfied” rule with explicit obligations and results.

**F09 — Declared dependencies do not execute as dependencies between providers. High modularity defect; reproduced.**

The provider protocol takes one request and returns a tuple of results. Orchestration invokes each provider once in binding-list order, passing the same request. It does not pass predecessor results to dependent providers. The topological sort occurs later, when assessing whether already-returned results satisfy obligations. [Provider protocol][provider-protocol] [Provider invocation][provider-invocation] [Post hoc dependency check][dependency-composition]

The probe splits a fact producer and its dependent rule into separate providers and reverses their binding order. The dependent rule is invoked first. More fundamentally, sorting invocation alone would not fix the absent input channel for computed predecessor facts.

A single provider can internally compute an entire pipeline; multiple providers can also arrange hidden shared state or duplicate each other's computation. Neither realizes the promised independently composable fact → assessment → rule model through the public protocol. Hidden coordination also weakens the meaning of an exact context and reproducible dependency evidence.

Repair: choose an explicit evaluation model. Either execute a typed acyclic graph with immutable predecessor values and well-defined state/commit semantics, or restrict providers to independent contributions and narrow the language accordingly. The first option changes the provider protocol, scheduling, evidence model, and composition algorithm.

**F10 — Support aggregation gives optional advice a veto and cannot admit a bounded effective level. Medium-to-high availability/semantic defect; reproduced.**

Support checks demand resolved, `exact` support for every selected binding, independently of whether its slots are mandatory or advisory. A probe with only advisory slots, failed results, and unsupported provider support makes the entire composition `unsupported`. MPC-06 says missing or failed optional advice is lost advice and grants no permission; it does not itself acquire a veto. [Support reducer][support-reducer] [MPC-06][mpc-advice]

An explicitly authorized bounded support record similarly produces `weakened` with a blocking support cause. Refusing a weakening of a mandatory obligation under its original admission is correct. The deficiency is that the selection model provides no useful expected-strength relation with which to admit a genuinely bounded realization as satisfying a bounded requirement. Descriptive downgrade records do not supply that relation.

Repair: compute mandatory dependency closure and required support per obligation; preserve optional diagnostic failure without turning it into global denial. Represent admitted support strength explicitly. Do not simply allow every downgrade or ignore failed prerequisites of mandatory work.

**F11 — The published IFC vocabulary cannot express the owner-relative generality, and extension is hardcoded. High design limitation.**

The security profile fixes confidentiality to `restricted`/`unknown` obligations and integrity to `endorsed`/`unknown`/`untrusted`. Its contract requires the exact digest of that one published profile. Modular profile validation recognizes only that profile and `teaching-influence/rev1`; the latter has two fixed educational tokens. [Security profile][security-profile] [Exact profile restriction][flow-profile-contract] [Modular profile switch][profile-switch]

The finite product/powerset algebra is meaningful, but generic `restricted` does not itself distinguish Alice's information, Bob's information, two incomparable reader sets, or independent owners' release authority. A trusted resolver could recover such distinctions from provenance and external policy, but then those distinctions are not represented by the claimed portable label semantics. The difficult policy has moved into opaque interpretation.

Similarly, adding another domain requires changes to closed core Python alternatives and profile switches. A governed publication process for new semantics is reasonable; treating two enumerated examples as a sufficient extensible-domain mechanism is not. Owner-relative information-flow systems need an explicit representation of whose policy applies, not just a generic restrictive bit. [Primary reference: decentralized label model](https://www.cs.cornell.edu/andru/papers/sp98/paper.html)

Repair: specify a bounded, typed parameterization or publication/registration mechanism for domains, principal-qualified obligations, joins, release authority, and unknowns. Keep arbitrary provider code and participant-chosen interpretation outside that mechanism. If the intended scope is only the current tiny universes, narrow the claims and document their application limits instead.

**F12 — “Inject” realization is status-view serialization, not the declared inject lifecycle. High integration/evidence defect.**

The modular effect owner maps `inject` to `deliver_participant_directed_view`. That operation accepts a `ParticipantStatusViewModel` and serializes it as a participant-inject-delivery crossing. The runtime binding checks participant, episode, view identifier, state cut, and disclosure projection. It does not create a fresh DSL-111 inject occurrence or execute the referenced inject/event/script/story content chain. [Inject owner binding and submission][effect-owners] [Directed-view operation][directed-view]

Trusted context validation of the static DSL-142 declaration is useful, but cannot establish that the declared inject content was realized. The effect dispatcher discards the returned view and takes its outcome from the durable operation record; it has not thereby obtained evidence of a recipient boundary receiving that content.

An in-process return can legitimately define a delivery boundary when the consumer and acknowledgment semantics are explicit. The defect is the unestablished connection between the declared inject, fresh execution occurrence, actual content, and receiving boundary. The directed-view method itself correctly says that it does not prove participant observation; that restraint should extend to the broader realization claim.

Repair: have the shared runtime connect the existing orchestration owner to a fresh occurrence, bind content and target identity, invoke the concrete delivery mechanism, and record delivery from evidence at the declared receiving boundary. Preserve the separate observation claim. This needs integration across authoring, runtime orchestration, and backend realization, rather than another name or reference field on a status carrier.

**F13 — Mixed runtime records mappings without realizing them and fabricates delivery/observation from success. High correctness/evidence defect.**

Mixed dispatch selects participant/action allocations and a crossing edge, records mapping references and loss, and routes the same action request to a component's participant runtime. The coordinator does not execute the declared translation or time mapping through a bound adapter/scheduler on this path. [Mixed dispatch preparation][mixed-dispatch] [Backend invocation][action-effect]

A backend wrapper could perform translation internally. That possibility does not establish that the coordinator applied the admitted edge's particular mapping or enforced its temporal semantics. The implemented subset is better characterized as allocation-aware provider routing until those obligations are bound and observed.

The stronger defect is direct: `record_mixed_action_result` receives a success boolean and, when true, unconditionally appends a succeeded delivery event and a committed observation event. It receives no delivery or observation evidence. Successful action execution does not imply either event. [Mixed result recording][mixed-result]

Repair: refuse or explicitly narrow unsupported edge semantics; bind translation and time coordination to their actual owners; obtain distinct result, delivery, and observation records. Revisit admission capabilities and ADR-102's realized scope. The mixed demonstration and claim-reconciliation issues are still open; this review does not treat them as completed evidence, but #1016's implemented histories are already overstated.

**F14 — Formal analysis is appropriately bounded, but native runtime assurance is partly synthetic. High evidence-integrity defect.**

The finite opacity analyzer, normalized-model reachability analysis, and Isabelle work have real, limited value. The theorems concern declared abstract relations and assumptions; they do not establish a refinement from live participant execution to that model. Bisimulation design is also not a completed implementation: all six implementation descendants, #971–#976, remain open outside milestone 67. [Opacity formalization][opacity-proof] [Bisimulation ADR][adr100]

Runtime opacity currently normalizes supported decisions to uniform denial. The published runtime profile explicitly excludes a useful allowed-action/delivered-view case. Uniform denial can satisfy confidentiality while providing no useful participant interaction. This is an honestly disclosed limitation, not a refutation of the mathematics; it does mean “opacity enforcement implemented” is a poor proxy for usable participant control. [Opacity normalization][opacity-normalize] [Runtime profile][opacity-profile]

The reference backend's `participant_relation_probe` validates profile/point identifiers and returns a constant observation dictionary. It does not execute the claimed crossing, retry, or delivery behavior. The conformance case labels the realization `BACKEND_NATIVE` and its execution basis `hermetic-live`, then consumes that dictionary. This is an asserted transcript being treated as observed operational evidence. [Reference probe][opacity-probe] [Conformance observation][opacity-conformance]

Repair: retain the bounded mathematics and make it an optional analysis facility with explicit interpretation obligations. Separate specification witnesses, simulated transcripts, instrumented backend observations, and deployment claims in evidence provenance. A native claim needs an actual native execution trace at the relevant boundary. The issue here is what the evidence establishes, not how many tests exist.

**F15 — A final egress denial can be durably recorded as a succeeded operation. Medium-to-high, localized correctness defect.**

Initial crossing artifact construction marks a permitted operation `SUCCEEDED`. If the later SEM-233 final egress sink denies release, `_with_flow_sink_denied_audit` changes the audit event but leaves the operation record's succeeded status intact. The path commits that prepared crossing and raises `PermissionError`. [Initial operation status][crossing-operation] [Final egress denial][egress-denial]

The immediate caller is denied the data; this finding is not an initial-call disclosure. It is a disagreement between authoritative-looking durable artifacts about what happened. Status/readback consumers, recovery, and effect realization cannot safely equate that success record with completed delivery. The ingress denial path already demonstrates that operation state can be corrected explicitly.

Repair: derive the terminal status from the final outcome, preserving intermediate gate decisions as intermediate evidence. This is a small implementation fix with a consequential semantic invariant.

**F16 — Provider execution can monopolize control, and history processing grows with the entire run. Medium operational-design concern.**

Providers execute synchronously inside the control-plane mutation regime. The external-call fence prevents unsafe reentry, but does not supply a deadline, cancellation protocol, or isolation boundary. Causal attempt/fanout/depth limits count semantic activity; they do not bound a provider that never returns. A hanging provider can therefore prevent further mutations through that authority, including control intended to interrupt or shut down activity. [Provider invocation][provider-invocation] [Mutation authority][mutation-authority]

The shared runtime needs a supervisory path that can remain effective when ordinary provider execution is blocked, with backend-specific termination or containment mechanisms available through explicit protocols. An external backend supervisor may additionally terminate a worker or service, but its availability does not establish that the runtime's own interruption contract works.

History handling adds a separate scaling concern. Crossing append reconstructs and validates accumulated history; modular causal-state lookup and effect draining reparse accumulated evaluations. Repeated full-history work creates at least quadratic cumulative processing in relevant append paths as the run grows. This is an algorithmic observation, not a benchmark or claimed production latency. [Crossing history append][crossing-history] [Causal-state fold][causal-state] [Effect-history scan][effect-scan]

Repair: specify provider resource/deadline obligations and an independently effective supervisory path in the shared runtime, including the concrete interruption capabilities required from backends. Use incremental validated state and bounded/indexed readback while retaining immutable evidence history. Treat these as production runtime responsibilities, and evaluate established execution and supervision foundations before implementing further custom machinery.

**Cross-cutting diagnosis**

The recurring modeling error is to collapse distinct layers:

| Distinction the system needs | What the implementation sometimes substitutes |
| --- | --- |
| Policy template versus execution occurrence | Authored fixed revisions and order |
| Scenario subject versus supervisor versus principal | Controller as scenario agent, credential acting for it |
| Required obligation versus declared installation | Required profile appears in a binding list |
| Executed dependency versus declared dependency | Post hoc satisfaction over independent results |
| Permission to attempt versus completed effect | Accepted control occurrence or successful operation |
| Execution result versus delivery versus observation | Three records generated from one success boolean |
| Abstract witness versus measured realization | Constant probe transcript labeled live native evidence |

Additional schemas and references do not repair these substitutions. They can make the records internally consistent while leaving their connection to the underlying behavior unestablished. The shared runtime architecture needs fewer ambiguous concepts and clearer operational meanings at its boundaries.

**What should survive**

There is no evidence-based reason to discard the whole language or every milestone artifact. Preserve and build around:

- World truth, participant-facing views, participant history, and archival assurance as different information surfaces.
- Authentication, scoped authority, action admission, declassification, and endorsement as separate decisions.
- Decision, approval, execution, delivery, and observation as distinct events; make the implementation honor the distinction.
- Exact state cuts, immutable identities, history-head/CAS checks, and explicit stale-context refusal.
- Commit-before-dispatch and honest indeterminate recovery instead of invented exactly-once guarantees.
- Explicit capability subsets, conditional formal results, and the distinction between directional conformance and bisimulation.
- One shared RAE runtime driving execution through backend protocols, with common coordination and control semantics reused across LilRAE, BigRAE, and other backends.
- Backend realization of concrete effects and environment-specific protection, and the declared-world distinction between in-world adversarial behavior and attacks on the hosting infrastructure.
- The rule that legacy history does not retrospectively become governed evidence.

The existing parser/compiler infrastructure, broad contract infrastructure, operation-store machinery, and bounded formal analyzers should be evaluated for reuse at these boundaries. Their existence is not the problem. Reuse should not force the redesigned semantics back into the old shapes.

**Repair size and sequence**

This is a **multi-month subsystem redesign with several bounded fixes that should happen earlier**. It is not a credible one-PR cleanup, nor is there evidence that all of RAES needs replacement.

The milestone's delivery changes touch 821 distinct paths, of which 785 exist at the audited revision. The current affected Python production files number 169 and contain about 45,900 lines; affected documentation and formal specifications span another 202 files. These figures describe the change radius, not lines introduced by the milestone or lines requiring replacement. Shared files contain older and later work; generated schema fan-out is substantial. They establish that this is cross-cutting, not a reliable effort multiplier.

| Work package | Relative size | Main output and dependency |
| --- | --- | --- |
| Contain misleading behavior and claims | Small–medium | Fix v2 context forwarding and egress status; remove synthetic observation/native-evidence claims; explicitly restrict unsupported control selections and effects. Can start before the full redesign. |
| Clarify shared-runtime and backend execution boundaries; assess reusable foundations | Medium–large | Preserve RAE's common orchestration role; define concrete backend invocation/readback obligations and evaluate foundations within or beneath the runtime. This guides the architecture repair. |
| Redesign participant/controller/authority and transition model | Large | Independent roles; reusable policies; live occurrences, revocation and intervention semantics. Authoring/compiler/contract migration required. |
| Redesign modular composition and profile extension | Very large | Required applicability, typed provider dataflow, optional advice, admitted support strength, qualified IFC domains, and coherent effect phases. Revise ADR-108/SEM-235/API-424 together. |
| Complete shared-runtime effect execution through backend protocols | Large | Runtime coordination of cancellation/handoff, fresh inject occurrences and delivery; supported-effect admission, concrete backend enforcement, and recovery readback. Depends on the corrected contracts. |
| Make participant and administrative interfaces distinct | Medium–large | A separately scoped participant interface or consistently scoped capabilities, preserving the shared runtime's authorization boundary across backends. Choice affects API migration. |
| Complete or narrow mixed realization | Large if retained at present ambition | Real translation/time owners and independently observed event provenance. A narrower declared router is a smaller legitimate deliverable. |
| Rebuild assurance claims and migrate publications | Medium–large, ongoing | Evidence provenance, model-to-runtime interpretation, versioned schemas/docs, and explicit handling of old records. Native realization effort belongs with each backend. |

For planning, treat the local containment work as days to a few weeks, and the semantic redesign, implementation, documentation, and migration as a multi-month effort across language/contracts and runtime/backend expertise. This estimate rests on the remaining concrete findings, not the withdrawn ownership objection. A more precise staffing or engineer-month estimate requires decisions about reusable runtime foundations, supported capabilities, and LilRAE/BigRAE integration requirements. Reusing established machinery or narrowing the supported feature set may reduce implementation work; the semantic and evidence defects still require explicit correction.

The first design deliverable should be a small set of concrete operational stories with explicit ownership and evidence: an external supervisor repeatedly approving work; an intervention racing with backend execution; a required provider being unavailable; one provider consuming another's fact; an inject reaching a recipient; and a mixed action succeeding without yet being delivered or observed. These expose the missing semantics directly. Resolve them before generating another large family of contracts or accumulating more downstream implementation against the current shapes.

Do not make formal sophistication the release gate for ordinary useful behavior. Establish a coherent, bounded participant-control path through the shared runtime and one complete backend, demonstrate its actual effects and refusals, and then drive an additional backend through the same runtime to assess portability. Make stronger analysis or cross-backend claims only over evidenced realizations.
